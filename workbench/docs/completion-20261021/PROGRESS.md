## 检查点 2：整包范围核查、人工记录、运行对比与恢复

已实现的完整软件路径：

1. 精确冻结输入 → 显式执行准备 → 保存逐条依赖计划 → 显式启动范围核查。启动、任务、outbox、幂等回执与审计在同一事务提交；API 与 Worker 使用不同的非 owner 角色。

## 检查点 4：编写、生成物采用与独立解析

本轮实现范围：

1. 资料页进入章节编写，编写页回到包与原件。实际 Rich 路由已注册；编辑器保存表格、合并单元格、精确图片版本、稳定节点与引用，继续使用原保存队列与修订 CAS。文字 schema 切换到 Rich schema 后重新建立对应编辑视图，防止旧图片与粘贴处理器继续使用错误 schema。
2. 构建绑定明确的 draft、revision、snapshot、input、manifest、writer 与原请求，历史按单条明确展开。申请先保存恢复记录；未知或不匹配 ACK、幂等冲突与网络不确定均保留原 key/body。DOCX 与 PDF 成功状态、下载和部分覆盖分别呈现。
3. 用户选择成功生成物、包、用途及分册后，按包 ETag 追加新修订，保留旧成员，不改材料、正文或评审 head。采用核对构建与发布回执、固定快照、原件字节、来源闭包和完整当前编写资格；受控 PDF 另核对同次 Word、转换关系及渲染身份。
4. 已采用文件后续进入冻结、准备或新核查时再次检查生成资格。依据撤回、正文依据变化、计划／格式确认撤回或图片资产失效会阻止新用途；历史文件与原 ACK 保持可读。
5. 新增独立 `document-parse/1`／`parse-document` 路径：精确已核验 PDF → 固定方法申请 → 普通 document Worker → 解析结果。原件读取与 PDFium／解析器调用位于事务外，取消、关闭、撤回与迟到结果均受发布围栏约束。完成只刷新解析目录，用户仍须明确选择版本与物理页段；不自动切换正文或启动核查。
6. 独立解析结果完成后封闭页和证据追加，数据库约束与行锁保护结果不可变；旧 RR 快照不能绕过后提交的结果封闭。默认 PDFium 明确只提供部分文字覆盖，不声称 OCR、表格、图片或 Word 完整覆盖。
