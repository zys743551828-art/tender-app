# 条款修订、历史导入与知识引用验收

本检查点补齐三个实际入口：精确要求清单的有据人工修订、历史实交清单的预检查及确认、知识版本关联指定整包核查。它们继续使用同一套项目身份、来源、命令回执和审计。实际模型效果、要求语义完整性与正式投递资格不由本检查点授予。

## 1. 要求清单的有据人工修订

在已选择的要求清单下，用户可以补充条款、替换明确的旧条款，或记录人工不采用。每项必须选择该清单已经冻结的权威依据、逐字原文和页段，并核对完整前后差异。评分条款保留精确十进制满分、分档及对应引文；没有满分证明时不能凭人工输入取得正式评分资格。

保存会产生新清单和不可变派生链。原机器抽取回执保持原样，`human_derivation` 单列人工链头、摘要与长度，不伪造另一轮抽取。每一个旧要求都有明确映射；语义未变的条款可以保留真实原决定，语义变化的条款不能继承旧确认。人工不采用不表示权威要求已经失效，也不表示风险已经解决。

新清单的证据根、依赖输入及执行计划识别派生链。旧 `/1` 依赖计划仍能按原身份读取；新用途须满足当前协议。修订后需要基于新清单重新冻结、准备与核查，旧报告和旧清单不改写。

### 实际入口与约束

路径前缀为 `/api/v1/bids/{bid_id}/packages/{package_id}/revisions/{revision_id}/requirement-inventories/{inventory_id}`。

| 方法及后缀                                    | 作用                                                            |
| --------------------------------------------- | --------------------------------------------------------------- |
| `POST /rule-corrections/preview`              | 在只读快照中计算完整差异及预览摘要                              |
| `POST /rule-corrections`                      | 原件锁外核验后，在最终事务中核当前身份、来源和 CAS 并生成新清单 |
| `GET /rule-corrections`                       | 分页读取原清单的修订目录                                        |
| `GET /rule-corrections/{correction_id}`       | 读取不可变保存结果和原命令身份                                  |
| `GET /rule-correction-evidence`               | 分页读取该清单的精确权威证据目录                                |
| `GET /rule-correction-evidence/{evidence_id}` | 读取精确完整证据，不用最新解析替代                              |

一次请求最多 100 项修订，清单最多 10,000 条，派生链最多 32 步；请求 1 MiB、预览 4 MiB、完整证明 64 MiB。超过限制明确拒绝，不裁切后保存。历史只读与新用途分开：关闭项目、撤回来源或存储不可用后，已经提交的原命令回执仍可以恢复；新修订继续受当前资格约束。

前端在回执尚未核对时保留原 key、body、ETag 和精确路径。刷新后先恢复原请求，正确匹配完整回执后才清理本地记录。选择其他清单不能静默丢掉未确认请求。

## 2. 历史清单预检查与确认

新增批次目录和原清单读取；保存预检查、确认与原键恢复沿用真实 `commands`。读取目录不创建新批次。目录时间来自原创建审计，缺审计不补造时间；原清单从实际对象存储读回，并核字节与摘要。

确认只接受空对象 `{}` 和该批次 ETag。修改记录必须重新预检查，不能在确认时替换原清单。预检查最多 1,000 条，完整规范清单最多 8 MiB。确认前读取待处理记录精确文件元数据，关闭数据库连接后流式核验实际提交文件、提交依据和可选官方来源；同一 blob 只读取一次，唯一原件总预算为 1 GiB。

| 情况                         | 实际行为                                             |
| ---------------------------- | ---------------------------------------------------- |
| 原件缺失或大小／SHA 不符     | 对应记录失败，合法记录仍可完成；失败行保留具体原因   |
| 存储暂时不可用               | 整个确认不提交成功回执，可以使用原键和原请求恢复     |
| 原件定位或输入在 IO 期间变化 | 最终事务再次核对，拒绝相应记录，不登记错误事实       |
| 回执丢失后原清单已不可读     | 已提交命令先返回原回执，不重复读文件或新增实交       |
| 同键不同请求                 | 拒绝幂等冲突，不将其当作原请求成功                   |
| 部分成功后再次处理           | 原成功与重复记录保留，只为明确失败／冲突行准备新清单 |

真实原件校验收据保存在提交依据和审计中，不暴露私有对象 key。原件可读不等于平台接受、来源当前有效、提交当时身份已确认或样本已经准入。

前端入口位于历史档案。它读取本地 JSON 清单，严格校验 UUID 和带时区时间，保留微秒，核对服务器原清单摘要；预检查与最终确认是两次明确操作。待确认命令刷新可恢复，通用 422、412、503 或不匹配响应不能被当成已经成功。

## 3. 知识关联指定整包核查

新增 `/api/v1/bids/{bid_id}/knowledge-reference-targets`，只读返回本项目真实整包核查目录，含精确包修订、要求清单、冻结输入、输入摘要和结果摘要。前端须明确选择一次核查，不能用当前项目或最新运行代替。

知识引用继续核发布版本、用途、适用范围、当前项目及来源祖先，保存引用前后严格校对对象身份。引用只是该次核查的参考注记，不修改原冻结输入、机器判断、人工意见或正式评分资格。新目录分页、鉴权与私有不缓存响应均已接通。

## 5. 部署与未授予的资格

新建库计划在既有要求、依赖及运行权限之后安装 `bid-package-rule-corrections.sql`。Fusion 预览推进为 `fusion_v11`，使用新的初始化与 API 配置卷，保留 v10 及更早卷。它仍是 API／Web／PG 预览，不包含 Kafka、S3 或运行消费者。Nginx 仅对历史预检查精确路径开放 9 MiB 请求预算，以容纳规范 8 MiB 清单；全局 5 MiB 和图片专用 12 MiB 保持各自范围。

要求质量仍为 `not_measured`，语义完整性与正式提交资格保持未授予。人工确认数量、成功导入记录和知识引用不会把未知改为通过。本检查点不关闭真实资料质量、整包标准提交与结果／指标适配、最新完整 schema 恢复或业务验收；后续实现继续在同一交付分支推进。

浏览器回执摘要分别见 [条款修订](rule-correction-browser-receipt.json)、[历史导入](historical-import-browser-receipt.json)、[知识引用布局](knowledge-target-browser-receipt.json)，保留输入与截图摘要；不将合成浏览器网络冒充真实业务端到端。
