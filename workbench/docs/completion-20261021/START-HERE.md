# 从这里开始：启动与操作验收

本页对应 `work/bid-workbench-completion-20261021` 的本轮实现。先选运行环境，再按下面两条路径操作；每一步以页面的实际状态和回执为准。代码发布状态、验证结果和剩余工作统一见 [PROGRESS](PROGRESS.md)。

## 1. 先选运行环境

| 环境            | 实际组成                                                                                 | 适合做什么                                                                             |
| --------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Fusion v12 预览 | PostgreSQL、初始化服务、API、Web；入口 `http://127.0.0.1:5188`                           | 登录、查看项目、编辑文字草稿、检查导航、真实空状态和未配置提示；已有历史按实际数据读取 |
| 完整本地运行    | PostgreSQL、Kafka、私有 S3、API，以及分别启动的 Worker；默认 Web `http://127.0.0.1:5173` | 在对应能力已配置的前提下，实际上传、构建、解析、核查、对比和导出                       |

**Fusion v12 是 API 预览环境。** [Compose](../../deploy/compose.fusion.yaml) 没有 Kafka、S3 或 Worker；[API 启动器](../../deploy/fusion_runtime.py) 只注入数据库、站点和会话配置，不提供模型、存储或转换器配置。页面可打开、请求被受理，都不表示后台任务已经执行。v12 使用新预览库和运行配置卷，保留 v11 及更早卷，不自动迁移旧预览项目数据。

### 已具备 Fusion 镜像的本机：打开预览

在仓库的 `workbench/` 目录，用 PowerShell 7 执行。先按 [本机环境说明](../fusion-local-checks.md) 准备 Node 等依赖；[启动脚本](../../deploy/fusion.ps1) 检查的三个镜像须已存在，它不会自动安装镜像。首次启动前，由你设置本机私有文件 `.local/fusion/admin-password`；登录名为 `admin`，口令取该文件，已有凭据不会被脚本重置。

```powershell
Push-Location apps/web
npm ci
npm run build
Pop-Location
pwsh -File deploy/fusion.ps1 -Action config
pwsh -File deploy/fusion.ps1 -Action up
pwsh -File deploy/fusion.ps1 -Action status
```

打开 `http://127.0.0.1:5188`。启动失败时用 `pwsh -File deploy/fusion.ps1 -Action logs` 查看原因；结束时用 `-Action stop`。新库中的空项目、空历史属于实际状态，系统不会补造业务结果。

### 要实际处理文件：配置完整运行环境

依照 [README 的运行步骤](../../README.md#运行) 创建独立配置，启动基础设施，初始化**全新空库**、主题和私有 bucket，再创建成员并分别启动进程。该说明中的旧切片范围和 `execution-policy-07.json` 是历史记录；当前主题初始化默认策略是 [`execution-policy-10.json`](../../apps/worker/execution-policy-10.json)，当前数据库装配见 [注册验收](registration-acceptance.md)。已有资料库不能重复初始化；旧库升级需要单独的迁移方案。

以下入口均来自仓库 [Worker CLI](../../apps/worker/__main__.py) 和 README，必须在已经配置的环境中启动：

| 进程入口                                   | 职责                                                   |
| ------------------------------------------ | ------------------------------------------------------ |
| `python -m apps.api`                       | 登录、权限、读写业务记录、受理任务；使用 API 身份      |
| `python -m apps.worker relay`              | 将数据库 outbox 中的已提交任务发送到 Kafka             |
| `python -m apps.worker consume`            | 文档通道：独立 PDF 解析、受控 Word 处理及派生索引      |
| `python -m apps.worker consume-export`     | 正文构建、核查报告文件生成；PDF 另需可用的受控转换能力 |
| `python -m apps.worker consume-comparison` | 比较通道；不调用模型                                   |
| `python -m apps.worker reconcile`          | 处理租约失联等运行对账                                 |

`python` 指已安装锁定依赖的虚拟环境解释器。API 与 Worker 使用各自非 owner 身份；owner 只用于初始化。已有独立 QA 配置时，可通过 [`deploy/run.py`](../../deploy/run.py) 显式选环境和角色，例如在 Linux/macOS：

```sh
.venv/bin/python deploy/run.py --env-file .local/qa.env --role api -- .venv/bin/python -m apps.api
# 另一个终端；其余 Worker 入口也分别启动
.venv/bin/python deploy/run.py --env-file .local/qa.env --role worker -- .venv/bin/python -m apps.worker relay
```

QA 的基础设施、初始化方式、API 端口 `8801` 和 Web 端口 `5174` 均见 README 的 QA 段落。配置文件和凭据留在本机，不写入 Git。

**真实模型需要你明确配置供应商、凭据与费用边界，并明确启用相关消费者。** `consume-review`、`consume-assistant` 可能产生模型费用，不属于上面的默认启动清单。模型未配置时，应验证“不可执行”的原因和恢复流程；不能把它计为核查结果。本轮验收没有调用付费模型。

### 可选：接入已有的本机解析服务

完整运行环境可使用 [本地 PDF 解析端口](../../packages/parsing/README.md)，实际方法为 PDFium、pdfplumber 和 Tesseract CPU profile。它与默认仅提取文字的解析不同；安装依赖、核验 OCR 资产、能力边界均以该说明为准，请勿将解析依赖锁直接覆盖到现有 API 环境。

1. 在本机准备已校验的 OCR 资产，使用独立解析环境。私有 `.local/parsing.env` 保存 `PARSING_RUNTIME_URL=http://127.0.0.1:8812`、你本机生成的 `PARSING_RUNTIME_TOKEN`（至少 32 字符）和实际 `PARSING_ASSET_DIRECTORY`。配置文件权限为 `600`，令牌不写进命令参数或 Git。
2. 按解析端口说明，用明确的配置启动服务：

   ```sh
   .venv/bin/python deploy/run.py --env-file .local/parsing.env -- .venv-parsing/bin/python -m packages.parsing.server --port 8812
   ```

3. 在实际启动 **API 和普通 document Worker** 的各自私有配置中，设置与解析服务一致的 `PARSING_RUNTIME_URL` 和 `PARSING_RUNTIME_TOKEN`，随后使用前面的 `deploy/run.py --role api`／`--role worker` 方式启动。API 在读取条件和受理时取得方法身份，Worker 在计算时重新核对；仅配置其中一端不能形成一致的解析申请。API／Worker 的数据库角色仍各自独立，不共享数据库口令。只有解析进程需要 OCR 资产路径和重依赖。

地址必须是各进程实际可达的同一 `127.0.0.1` 服务；分离容器的回环地址彼此不同，不能直接套用这组同机命令。Fusion v12 的 API 配置白名单不包含这些键，本节属于完整运行环境。未配置令牌时使用默认文字解析；配置了令牌但服务不可达时会明确失败，不静默退回另一方法。

配置后重新读取原件的解析条件，确认方法为 `configured_local`，再明确申请。真实服务返回无缺口的 `usable`，且页级校验也通过时，独立解析保存为 `complete`；工程图和扫描页的实际缺口继续保留 `partial`。方法或源码改变后，旧请求不会悄悄换方法执行，应读取新条件后另行明确申请。该路径的真实 HTTP、非 owner PG、表格和 OCR 验证见 [本机解析集成验收](configured-local-parser-acceptance.md)。

## 2. 路径一：编写 → 精确构建 → 采用 → 独立解析

1. **进入项目「资料」。** 点击「打开章节编写与生成」，创建正文草稿或继续已有草稿。人工编写无需先配置模板或企业事实库。已配置完整 Word 接收能力时，可选择同项目原件生成结构导入候选，核对章节、表格、图片和转换限制后明确追加；详见 [Word 导入验收](word-rich-import-acceptance.md)。
2. **保存正文。** 编辑章节、文字和已具备能力的表图，确认保存成功及当前修订。选择需要的目录、版式和格式，按界面要求确认编写依据。
3. **建立精确构建。** 构建绑定这一次草稿修订和固定快照。打开「生成记录」中的指定记录，分别看 DOCX 和 PDF 状态；Word 成功不代表 PDF 成功。仅下载成功且通过实际字节核验的文件。
4. **明确采用到包。** 在成功文件上选择「选择投标包并采用此文件」，指定包、用途和分册，保存包新修订。未解析时可先保存原件；采用不会自动替换当前正文，也不会启动核查。PDF 新用途还须满足受控生成资格。
5. **明确申请原件解析。** 打开「投标包与原件解析」，展开「解析原件与查看历史」，点击「读取当前解析条件」，填写理由后点击「明确申请解析此文件版本」。此路径处理精确 PDF；Word 原件须先取得受控 PDF。读取历史不会自动重跑。
6. **明确选择解析与页段。** 解析结束只刷新目录。回到包编辑，选择指定解析版本和物理页范围，保存下一包修订；系统不会自动选择“最新解析”。更换解析后，应重新核对页段。

### 为什么解析成功，仍然不能完整冻结？

任务 `succeeded` 表示本次计算完成；`coverage=partial` 表示内容覆盖仍有缺口。默认 PDFium 只提取物理页文字，没有证明扫描图、复杂表格、图片和全部内容已完整读取，因此始终保留 partial。即使列出了所有页，也不能据此认定所有内容已解析。

可以查看结果和原页，并保留未解析的原件包修订；**不能把 partial 选成包的完整冻结解析**。后续依赖完整解析的冻结、准备和核查会受阻，须配置并验证满足覆盖要求的解析能力。不要修改状态字段绕过这个门槛。具体边界见 [编写与解析验收](authoring-m1-acceptance.md)。

### 多章节 AI 建议：明确预算 → 核对完整候选 → 一次应用

在编写区域打开「多章节批量编写」。完整环境须先安装可选助手／预算／批次扩展，并配置真实可核验的模型、价格、额度和 Worker；默认 Fusion 预览只显示当前未配置原因，已有历史仍可查阅。配置与验证范围见 [M2 验收记录](authoring-m2-acceptance.md)。

1. 选择本批章节，逐章填写编写目标、资料来源、输出上限与累计额度，再明确批次总额和理由。系统先保存当前编辑，随后按确切修订冻结本批输入；不会替你默认填入付费预算。
2. 查看各章任务和费用。生成完成而候选尚未发布时继续等待整理；失败章节只有在原费用核清且剩余额度足够时才能明确重试，所有尝试费用仍计入原额度。
3. 逐章打开完整前后稿，核对实际文字变化、表格、图片及引用，再勾选希望应用的候选。未打开、未核对完整图片或已过期的候选不能选用。
4. 所有任务终结、费用核清后，填写确认理由并一次应用所选章节。任一草稿或来源冲突都会拒绝整次应用；未选章保持原样。本批随后结束，继续编写须基于新修订创建新批次。
5. 需要放弃时明确关闭本批；这会请求取消未完成任务，已发生或未知费用仍如实保留。遇到回执未确认，使用「恢复原批次请求结果」，沿用原键和原请求，不创建新的模型尝试。

## 3. 路径二：冻结输入 → 核查 → 人工意见 → 复检对比 → 报告

这条路径需要有效的招标／投标包、精确解析与页段、要求清单，以及对应的执行配置。路径一产生的新文件只有通过这些条件后才能作为新输入；默认 partial 解析不能直接贯通全部步骤。

1. **选择包与要求。** 核对招标依据、补遗、投标各册、用途、版本和页段；读取缺册、来源失效或解析缺口。确认要求清单后保存精确冻结输入。
2. **准备输入与依赖。** 对选定冻结输入明确执行准备，核对事实适用范围，逐条标注依赖并保存计划。声明容量与实际执行容量不同；当前范围核查最多 400 条要求、4 批，超限会拒绝，不会静默截断。
3. **明确开始核查。** 在「保存与查阅依赖计划」中打开指定计划，点击「选择这份计划继续核查」，再点击「开始整包范围核查」。查看真实排队、执行、取消或失败状态；读取历史不触发模型调用。
4. **查看结果并记录人工意见。** 按要求逐条定位原页，分别记录确认、不采用或需要复查。人工意见与机器结果分开保留；“确认判断”不表示风险已经解决。
5. **明确复检并选择两轮对比。** 同一输入通常返回原运行；确需再次执行时，按界面明确准备复检并填写理由。随后手动选择同项目的两个成功运行，核对输入、要求、机器判断和人工意见的变化。差异本身不证明风险消除。
6. **生成核查报告副本。** 先读取报告依据，再按可用能力申请 Word／PDF；报告固定原机器结果和申请时的人工意见版本。文件不会随后续意见自动变化，也不会再执行模型。报告是核查副本，不是投递正文或正式提交资格证明。

任何写入遇到“回执未确认”，优先使用原请求恢复入口，保留原键和原内容。不要通过反复新建任务猜测上一笔是否成功。项目结束、来源撤回或依据变化会影响新用途；既有历史仍按原身份查阅。

### 人工条款修订、历史导入与指定核查的知识参考

- **要求清单中的「规则修订」**：明确选择冻结原文，补充／替换条款或记录人工不采用，核对完整前后差异后保存新清单；随后重新冻结和核查。人工修订不会改写旧抽取回执或报告。
- **历史档案中的批量导入**：先读取 JSON 清单并保存预检查，再核对逐条结果和完整原清单，明确确认。确认实际核验原件，缺失或损坏的记录分别失败；部分成功后仅为失败／冲突行准备新清单。
- **知识版本的「引用位置」**：选择指定一次整包核查，核对包修订和输入摘要，再保存参考。知识注记与原核查结果分别保留。

回执未核对时，使用原请求恢复入口。详细容量、资格边界和实际验证见 [条款修订、导入与知识引用](rule-correction-import-acceptance.md)。

### 整包实际提交与官方成绩

1. 在提交工作面展开「整包提交检查与实交登记」，明确选择投标包和不可变修订。需求清单、范围声明与核查运行须逐项明确关联；不会默认采用最新正文或替换成另一个包。
2. 读取四类检查。当前完整资格尚未成立时，标准登记保持不可用。已经在线下提交的，可以选择事实补录，填写带时区的准确提交时间、原因及声明附件；服务端保存时重新核验实际原件字节。
3. 在已保存的整包卡片查看原件、原身份和登记时检查，或追加更正。原单正文与整包使用同一个实际提交历史，不另建第二个当前头。
4. 展开「登记／核验此整包的官方成绩」，填写技术／综合／未知口径、得分与满分、官方原件和取得时间。未知留空；真实零分填写 0。更正会追加新成绩，并重新进入待核验。
5. 核验时检查原工程／标段／轮次／主体与原招标依据，选择官方原页的逐字摘录，填写公布时间、聚合方式和说明。来源撤回后会显示当前不可用，原核验历史保留；不会自动获得训练样本或正式评分资格。
6. 断网或回执不明时先「恢复原操作」。出现版本冲突后，重新读取并明确采用核对后的版本才能继续，输入仍保留；不能自动覆盖另一个成绩头。

详细范围与原生数据库、浏览器证据见 [整包实交与成绩验收](package-submission-outcome-acceptance.md)。最新全部结构的数据库／原件恢复见 [当前 schema 恢复验收](current-schema-recovery-acceptance.md)。

## 4. 暂无完整配置时，怎样验收才有意义？

| 看到的情况               | 可做的有效检查                                                                                                                              |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------- |
| 新预览库没有历史         | 创建自己的项目和文字草稿，检查保存、继续编辑和切换项目；不把空历史当成测试数据丢失                                                          |
| 构建／解析一直排队       | 确认完整环境的 relay、对应消费者和 Kafka 已运行；Fusion 预览没有这些进程                                                                    |
| 存储、转换器或模型不可用 | 检查页面是否明确说明缺少什么，是否保留输入和恢复入口；能力配置完成前不期待成功文件或模型结果                                                |
| 解析完成但 partial       | 检查原页、覆盖缺口和禁止完整冻结的行为，这是当前默认解析的真实边界                                                                          |
| 想看结果页和异常交互     | 使用 [合成界面夹具说明](../../apps/web/qa-previews/frozen-inputs/README.md)；它明确模拟响应，不连接业务库，不证明真实模型效果或生成文件有效 |

夹具仅供开发验收，普通 Vite 构建会移除 `/_qa`；交付页面不应包含夹具目录。实际业务验收应使用明确授权的资料，在完整环境中核对精确文件、页码、结果和下载字节。
