# 从这里开始：启动与操作验收

本页对应fusion/bid-workbench主线。检查点1—16已合入，默认v14预览与独立完整运行组均已有本机Compose实测；可选研究能力仍须明确装配。先选运行环境，再按功能路径操作，以页面状态与实际回执为准。当前状态和剩余工作见[PROGRESS](PROGRESS.md)，完整文件链证据见[桌面Compose验收](desktop-runtime-acceptance.md)。

## 1. 先选运行环境

| 环境             | 实际组成                                                                                                                                        | 适合做什么                                                                             |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| Fusion v14 预览  | PostgreSQL、初始化服务、API、Web；入口 `http://127.0.0.1:5188`                                                                                  | 登录、查看项目、编辑文字草稿、检查导航、真实空状态和未配置提示；已有历史按实际数据读取 |
| 独立完整运行配置 | PostgreSQL、Kafka、私有 S3、API/Web、relay、reconcile、document/export/comparison Worker 及 Word/build 协调器；默认 Web `http://127.0.0.1:5189` | 用固定来源、角色和环境身份启动文件处理主线；模型通道与任务调度另行明确启用             |
| 手工启动已有 QA  | PostgreSQL、Kafka、私有 S3、API，以及分别启动的 Worker；Web 端口按已有 QA 配置                                                                  | 已有独立 QA 配置时调试指定进程；须核对其 SQL、主题与能力配置                           |

**Fusion v14 是 API 预览环境。** [Compose](../../deploy/compose.fusion.yaml) 没有 Kafka、S3 或 Worker；[API 启动器](../../deploy/fusion_runtime.py) 只注入数据库、站点和会话配置，不提供模型、存储或转换器配置。页面可打开、请求被受理，都不表示后台任务已经执行。v14 使用新预览库和运行配置卷，保留 v13 及更早卷，不自动迁移旧预览项目数据。

### 已具备 Fusion 镜像的本机：打开预览

在仓库的 `workbench/` 目录，用 PowerShell 7 执行。先按 [本机环境说明](../fusion-local-checks.md) 准备 Node 等依赖；[启动脚本](../../deploy/fusion.ps1) 检查的三个镜像须已存在，它不会自动安装镜像。首次启动前，由你设置本机私有文件 `.local/fusion/admin-password`；登录名为 `admin`，口令取该文件，已有凭据不会被脚本重置。

```powershell
Push-Location apps/web
npm ci
npm run build
Pop-Location
pwsh -File deploy/fusion.ps1 -Action config
pwsh -File deploy/fusion.ps1 -Action up
pwsh -File deploy/fusion.ps1 -Action status
```

打开 `http://127.0.0.1:5188`。启动失败时用 `pwsh -File deploy/fusion.ps1 -Action logs` 查看原因；结束时用 `-Action stop`。新库中的空项目、空历史属于实际状态，系统不会补造业务结果。

### 要实际处理文件：配置完整运行环境

Windows Docker Desktop 使用[完整Compose操作](desktop-runtime-runbook.md)，Linux私有目录方式见[独立完整运行说明](full-runtime-runbook.md)。配置器为新的环境冻结源码、SQL、前端、依赖和镜像身份，初始化全新库、9 个 Kafka 主题及私有 bucket，再按角色启动进程。API 与 Worker 使用不同的非 owner 登录和对象凭据；浏览器通过同源授权端点上传下载。默认不启动收费模型通道或定时任务运行器。

实际 Docker Desktop 已通过完整组、Linux私有卷、五角色权限与真实 nginx／Kafka／Worker 合成文件链，详见[桌面验收](desktop-runtime-acceptance.md)；验收组已停止，卷保留。此前原生主链与三类进程故障自然恢复见[原生验收](full-runtime-acceptance.md)和[故障恢复](real-transport-fault-recovery-acceptance.md)。这些分项不替代生产主机、转换隔离、容量或浏览器视觉验收。

以下为已有 QA 的手工启动方式；新完整配置的实际命令、固定组件及能力开关以其运行说明为准。

依照 [README 的运行步骤](../../README.md#运行) 创建独立配置，启动基础设施，初始化**全新空库**、主题和私有 bucket，再创建成员并分别启动进程。该说明中的旧切片范围和 `execution-policy-07.json` 是历史记录；当前主题初始化默认策略是 [`execution-policy-10.json`](../../apps/worker/execution-policy-10.json)，当前数据库装配见 [注册验收](registration-acceptance.md)。已有资料库不能重复初始化；旧库升级需要单独的迁移方案。

以下入口均来自仓库 [Worker CLI](../../apps/worker/__main__.py) 和 README，必须在已经配置的环境中启动：

| 进程入口                                   | 职责                                                   |
| ------------------------------------------ | ------------------------------------------------------ |
| `python -m apps.api`                       | 登录、权限、读写业务记录、受理任务；使用 API 身份      |
| `python -m apps.worker relay`              | 将数据库 outbox 中的已提交任务发送到 Kafka             |
| `python -m apps.worker consume`            | 文档通道：独立 PDF 解析、受控 Word 处理及派生索引      |
| `python -m apps.worker consume-export`     | 正文构建、核查报告文件生成；PDF 另需可用的受控转换能力 |
| `python -m apps.worker consume-comparison` | 比较通道；不调用模型                                   |
| `python -m apps.worker reconcile`          | 处理租约失联等运行对账                                 |

`python` 指已安装锁定依赖的虚拟环境解释器。API 与 Worker 使用各自非 owner 身份；owner 只用于初始化。已有独立 QA 配置时，可通过 [`deploy/run.py`](../../deploy/run.py) 显式选环境和角色，例如在 Linux/macOS：

```sh
.venv/bin/python deploy/run.py --env-file .local/qa.env --role api -- .venv/bin/python -m apps.api
# 另一个终端；其余 Worker 入口也分别启动
.venv/bin/python deploy/run.py --env-file .local/qa.env --role worker -- .venv/bin/python -m apps.worker relay
```

QA 的基础设施、初始化方式、API 端口 `8801` 和 Web 端口 `5174` 均见 README 的 QA 段落。配置文件和凭据留在本机，不写入 Git。

**真实模型需要你明确配置供应商、凭据与费用边界，并明确启用相关消费者。** `consume-review`、`consume-assistant` 可能产生模型费用，不属于上面的默认启动清单。模型未配置时，应验证“不可执行”的原因和恢复流程；不能把它计为核查结果。本轮验收没有调用付费模型。

### 可选：接入已有的本机解析服务

完整运行环境可使用 [本地 PDF 解析端口](../../packages/parsing/README.md)，实际方法为 PDFium、pdfplumber 和 Tesseract CPU profile。它与默认仅提取文字的解析不同；安装依赖、核验 OCR 资产、能力边界均以该说明为准，请勿将解析依赖锁直接覆盖到现有 API 环境。

1. 在本机准备已校验的 OCR 资产，使用独立解析环境。私有 `.local/parsing.env` 保存 `PARSING_RUNTIME_URL=http://127.0.0.1:8812`、你本机生成的 `PARSING_RUNTIME_TOKEN`（至少 32 字符）和实际 `PARSING_ASSET_DIRECTORY`。配置文件权限为 `600`，令牌不写进命令参数或 Git。
2. 按解析端口说明，用明确的配置启动服务：

   ```sh
   .venv/bin/python deploy/run.py --env-file .local/parsing.env -- .venv-parsing/bin/python -m packages.parsing.server --port 8812
   ```

3. 在实际启动 **API 和普通 document Worker** 的各自私有配置中，设置与解析服务一致的 `PARSING_RUNTIME_URL` 和 `PARSING_RUNTIME_TOKEN`，随后使用前面的 `deploy/run.py --role api`／`--role worker` 方式启动。API 在读取条件和受理时取得方法身份，Worker 在计算时重新核对；仅配置其中一端不能形成一致的解析申请。API／Worker 的数据库角色仍各自独立，不共享数据库口令。只有解析进程需要 OCR 资产路径和重依赖。

地址必须是各进程实际可达的同一 `127.0.0.1` 服务；分离容器的回环地址彼此不同，不能直接套用这组同机命令。Fusion v14 的 API 配置白名单不包含这些键，本节属于完整运行环境。未配置令牌时使用默认文字解析；配置了令牌但服务不可达时会明确失败，不静默退回另一方法。

配置后重新读取原件的解析条件，确认方法为 `configured_local`，再明确申请。真实服务返回无缺口的 `usable`，且页级校验也通过时，独立解析保存为 `complete`；工程图和扫描页的实际缺口继续保留 `partial`。方法或源码改变后，旧请求不会悄悄换方法执行，应读取新条件后另行明确申请。该路径的真实 HTTP、非 owner PG、表格和 OCR 验证见 [本机解析集成验收](configured-local-parser-acceptance.md)。

## 2. 路径一：编写 → 精确构建 → 采用 → 独立解析

1. **进入项目「资料」。** 点击「打开章节编写与生成」，创建正文草稿或继续已有草稿。人工编写无需先配置模板或企业事实库。已配置完整 Word 接收能力时，可选择同项目原件生成结构导入候选，核对章节、表格、图片和转换限制后明确追加；详见 [Word 导入验收](word-rich-import-acceptance.md)。
2. **保存正文。** 编辑章节、文字和已具备能力的表图，确认保存成功及当前修订。选择需要的目录、版式和格式，按界面要求确认编写依据。
3. **建立精确构建。** 构建绑定这一次草稿修订和固定快照。打开「生成记录」中的指定记录，分别看 DOCX 和 PDF 状态；Word 成功不代表 PDF 成功。仅下载成功且通过实际字节核验的文件。
4. **明确采用到包。** 在成功文件上选择「选择投标包并采用此文件」，指定包、用途和分册，保存包新修订。未解析时可先保存原件；采用不会自动替换当前正文，也不会启动核查。PDF 新用途还须满足受控生成资格。
5. **明确申请原件解析。** 打开「投标包与原件解析」，展开「解析原件与查看历史」，点击「读取当前解析条件」，填写理由后点击「明确申请解析此文件版本」。此路径处理精确 PDF；Word 原件须先取得受控 PDF。读取历史不会自动重跑。
6. **明确选择解析与页段。** 解析结束只刷新目录。回到包编辑，选择指定解析版本和物理页范围，保存下一包修订；系统不会自动选择“最新解析”。更换解析后，应重新核对页段。

### 为什么解析成功，仍然不能完整冻结？

任务 `succeeded` 表示本次计算完成；`coverage=partial` 表示内容覆盖仍有缺口。默认 PDFium 只提取物理页文字，没有证明扫描图、复杂表格、图片和全部内容已完整读取，因此始终保留 partial。即使列出了所有页，也不能据此认定所有内容已解析。

可以查看结果和原页，并保留未解析的原件包修订；**不能把 partial 选成包的完整冻结解析**。后续依赖完整解析的冻结、准备和核查会受阻，须配置并验证满足覆盖要求的解析能力。不要修改状态字段绕过这个门槛。具体边界见 [编写与解析验收](authoring-m1-acceptance.md)。

### 多章节 AI 建议：明确预算 → 核对完整候选 → 一次应用

在编写区域打开「多章节批量编写」。完整环境须先安装可选助手／预算／批次扩展，并配置真实可核验的模型、价格、额度和 Worker；默认 Fusion 预览只显示当前未配置原因，已有历史仍可查阅。配置与验证范围见 [M2 验收记录](authoring-m2-acceptance.md)。

1. 选择本批章节，逐章填写编写目标、资料来源、输出上限与累计额度，再明确批次总额和理由。系统先保存当前编辑，随后按确切修订冻结本批输入；不会替你默认填入付费预算。
2. 查看各章任务和费用。生成完成而候选尚未发布时继续等待整理；失败章节只有在原费用核清且剩余额度足够时才能明确重试，所有尝试费用仍计入原额度。
3. 逐章打开完整前后稿，核对实际文字变化、表格、图片及引用，再勾选希望应用的候选。未打开、未核对完整图片或已过期的候选不能选用。
4. 所有任务终结、费用核清后，填写确认理由并一次应用所选章节。任一草稿或来源冲突都会拒绝整次应用；未选章保持原样。本批随后结束，继续编写须基于新修订创建新批次。
5. 需要放弃时明确关闭本批；这会请求取消未完成任务，已发生或未知费用仍如实保留。遇到回执未确认，使用「恢复原批次请求结果」，沿用原键和原请求，不创建新的模型尝试。

## 3. 路径二：冻结输入 → 核查 → 人工意见 → 复检对比 → 报告

这条路径需要有效的招标／投标包、精确解析与页段、要求清单，以及对应的执行配置。路径一产生的新文件只有通过这些条件后才能作为新输入；默认 partial 解析不能直接贯通全部步骤。

1. **进入项目「整包核查」，选择包与要求。** 概览的下一步也会进入该工作区。明确选择包、修订和要求清单，核对招标依据、补遗、投标各册、用途、版本和页段；读取缺册、来源失效或解析缺口。确认要求清单后保存精确冻结输入。页面链接保留所选包／修订／清单，刷新和返回不会静默改用最新版；无效链接会保留错误原因。
2. **准备输入与依赖。** 对选定冻结输入明确执行准备，核对事实适用范围，逐条标注依赖并保存计划。声明容量与实际执行容量不同；当前范围核查最多 400 条要求、4 批，超限会拒绝，不会静默截断。
3. **明确开始核查。** 在「保存与查阅依赖计划」中打开指定计划，点击「选择这份计划继续核查」，再点击「开始整包范围核查」。查看真实排队、执行、取消或失败状态；读取历史不触发模型调用。
4. **查看结果并记录人工意见。** 按要求逐条定位原页，分别记录确认、不采用或需要复查。人工意见与机器结果分开保留；“确认判断”不表示风险已经解决。
5. **明确复检并选择两轮对比。** 同一输入通常返回原运行；确需再次执行时，按界面明确准备复检并填写理由。随后手动选择同项目的两个成功运行，核对输入、要求、机器判断和人工意见的变化。差异本身不证明风险消除。
6. **生成核查报告副本。** 先读取报告依据，再按可用能力申请 Word／PDF；报告固定原机器结果和申请时的人工意见版本。文件不会随后续意见自动变化，也不会再执行模型。报告是核查副本，不是投递正文或正式提交资格证明。

### 保存并运行整包手动任务

选用一份依赖计划后，可以点击「保存为手动任务」。表单带入已选整包修订、清单、冻结输入、执行准备和依赖计划；填写模板名称与说明后保存。保存不启动核查，也不选择其他输入。执行服务未就绪时仍可保存模板，运行时会重新检查条件。

在项目「可复用任务」找到模板，核对明确绑定的版本并手动启动。整包范围核查当前只支持手动触发；重新保存同一内容不会授权额外模型尝试。需要复检时，先在整包工作区明确准备含原因的新输入，再保存新的模板版本。任务结果保持部分覆盖与正式资格未授予的边界，并能回到原整包运行查看依据。

遇到网络失败或回执不一致，使用表单或卡片的原请求恢复入口，沿用原请求键、内容和条件头。模板后续修订、原运行完成或当前页面换了选择，都不能改写上一笔请求。版本冲突时保留输入，明确读取服务器的新基准后再保存；恢复原 ACK 与查看当前运行状态是两个不同操作。

任何写入遇到“回执未确认”，优先使用原请求恢复入口，保留原键和原内容。不要通过反复新建任务猜测上一笔是否成功。项目结束、来源撤回或依据变化会影响新用途；既有历史仍按原身份查阅。

### 人工条款修订、历史导入与指定核查的知识参考

- **要求清单中的「规则修订」**：明确选择冻结原文，补充／替换条款或记录人工不采用，核对完整前后差异后保存新清单；随后重新冻结和核查。人工修订不会改写旧抽取回执或报告。
- **历史档案中的批量导入**：先读取 JSON 清单并保存预检查，再核对逐条结果和完整原清单，明确确认。确认实际核验原件，缺失或损坏的记录分别失败；部分成功后仅为失败／冲突行准备新清单。
- **知识版本的「引用位置」**：选择指定一次整包核查，核对包修订和输入摘要，再保存参考。知识注记与原核查结果分别保留。

回执未核对时，使用原请求恢复入口。详细容量、资格边界和实际验证见 [条款修订、导入与知识引用](rule-correction-import-acceptance.md)。

### 整包实际提交与官方成绩

1. 在提交工作面展开「整包提交检查与实交登记」，明确选择投标包和不可变修订。需求清单、范围声明与核查运行须逐项明确关联；不会默认采用最新正文或替换成另一个包。
2. 读取四类检查。当前完整资格尚未成立时，标准登记保持不可用。已经在线下提交的，可以选择事实补录，填写带时区的准确提交时间、原因及声明附件；服务端保存时重新核验实际原件字节。
3. 在已保存的整包卡片查看原件、原身份和登记时检查，或追加更正。原单正文与整包使用同一个实际提交历史，不另建第二个当前头。
4. 展开「登记／核验此整包的官方成绩」，填写技术／综合／未知口径、得分与满分、官方原件和取得时间。未知留空；真实零分填写 0。更正会追加新成绩，并重新进入待核验。
5. 核验时检查原工程／标段／轮次／主体与原招标依据，选择官方原页的逐字摘录，填写公布时间、聚合方式和说明。来源撤回后会显示当前不可用，原核验历史保留；不会自动获得训练样本或正式评分资格。
6. 断网或回执不明时先「恢复原操作」。出现版本冲突后，重新读取并明确采用核对后的版本才能继续，输入仍保留；不能自动覆盖另一个成绩头。

详细范围与原生数据库、浏览器证据见 [整包实交与成绩验收](package-submission-outcome-acceptance.md)。最新全部结构的数据库／原件恢复见 [当前 schema 恢复验收](current-schema-recovery-acceptance.md)。

## 6. 技术范围、条件检查、报价与外观

报价工作区可明确选择投标包和招标补遗包，查看所选解析的报价条款，登记公式后试算并保存方案。切换包隔离草稿和待确认请求；历史方案仍按原公式及原输入查阅，来源改版后不会重新赋予当前使用资格。详见 [整包报价验收](exact-pricing-acceptance.md)。

登录和工作区顶栏均可选择“跟随系统／浅色／深色”，偏好在刷新后保留。原件画布保持白纸。主题及已验证范围见 [主题验收](theme-acceptance.md)。

全新 Fusion v14 预览已注册技术范围BASE结构；可选有据满分扩展需在 `technical-scale-authority.sql` 后安装 `technical-scale-package-identity.sql`，不在默认预览里隐式开启。分离测试库可使用 `FUSION_CHECK_SUITE=technical-scope-pure` 或 `technical-scope-api` 运行对应套件；不要指向业务数据库。

## 7. 触发任务、复盘和正文工作区

### 保存整包任务与查看触发记录

在整包工作面先核对确切包修订、清单、冻结输入、执行准备和依赖计划，再“保存为任务模板”或“先用文字拟定私有草案”。默认手动。只有明确选择资料更新或定时方式，模板才记录自动触发；它仍引用原输入，不会跟随最新包替换。定时表单保留时区、下一时刻和预算说明。

“可复用任务”内可展开“整包事件与定时触发记录”，查阅原事件／计划时刻、原模板版本、待决／已受理／阻断／取消状态。取消后回执丢失，应恢复原请求；受理之后到原生运行中查看结果。漏时只提示重新核对原模板，不补跑历史时段。站内通知不代表邮件或外部送达。

运行事件和定时任务还需要独立 coordinator／runner 服务及明确启用配置；Fusion 预览没有这些进程。保存模板不等于已执行，也不会因此启动本对话自动化。当前接通的是整包否决核对；其余任务类型仍须按各自能力状态判断。

### 从实际提交进入复盘

在“实交与成绩”展开“整包复盘与知识候选”，选择确切实交、官方结果、业务结果和两轮核查。缺少某类资料时填写具体缺失原因，不会补造结果。先预览依据，再保存不可变待核复盘；只有明确建立知识候选后，才能打开企业知识目录继续维护。候选不自动发布，也不授予研究样本或模型资格。

原核查、结果或来源后来变化时，历史快照保留；新流转会重新核验当前状态。收起复盘面板保留已挂载输入，退出账号或切换成员时清理对应浏览器恢复记录。

### 核对技术执行条件

在已保存或历史技术范围下，先明确选择量尺（也可保留未知），再读取正式执行条件。本版返回具体未满足项；执行基础的机制验收不等于正式评分可用。零预算申请只验证拒绝与零创建／零调用回执，不能产生分数。独立三次判断、预算和未知发送对账的机制入口仅供隔离验收库，未加入 BASE 或普通预览角色。

### 编写与文字差异

正文保持主区域，目录／编写管理按需展开。桌面助手与正文并排，并可用键盘或拖动调节宽度；窄屏使用可关闭的单任务面板。局部修改直接标出文字增删，多章 AI 候选可展开具体文字变化，同时保留完整表格／图片前后稿。长文按区块比较时仍保留两侧全文；看过差异不会自动应用候选或标记风险已解决。

新预览使用 37 项 BASE SQL，含整包技术范围、整包任务、事件／定时意图及待核复盘。旧未审 `retrospective-research.sql` 不在默认恢复计划中。备份恢复和各功能的本批证据见 [实施进度](PROGRESS.md)；请按该页区分合成机制、实际运输和仍待验证的真实业务效果。

## 8. 稿件与阶段：查阅确切历史

在项目「更多」中打开「稿件与阶段」，选择已保存草稿、生成记录、整包核查或实交记录，再从目录明确选择一条。刷新、返回和前进都保留原阶段、记录与选择摘要；首次进入不自动选择最新记录。目录不可用、空目录与本次刷新失败分别显示。

草稿可阅读全文、目录、表格和原图片；进入当前编辑稿有单独按钮。生成记录分别展示 Word／PDF 状态，只有成功文件提供下载；可回到生成时的快照，或打开有实际凭据的指定入包修订。核查与实交读取原记录，不启动新模型请求或补写业务状态。来源发生变化时保留历史，并显示读取时的变化或未知状态。

这是一处历史选择和查阅入口。新生成、核查或提交须回相应工作面重新检查资格。项目位置按当前成员与项目保存为浏览器偏好；未保存编辑和未核对命令继续受离开保护。桌面来源面板可拖动边界，或用左右方向键、Home／End 调宽，嵌套原件共用当前侧栏宽度。

### 本批可选服务的边界

历史研究核心、共同暴露守卫及元数据目录已有原生服务，安装顺序与实际权限见[历史守卫验收](package-history-exposure-bridge-acceptance.md)和[目录验收](package-history-directory-acceptance.md)。研究界面见第10节；独立CPU派发的额外SQL、单用途进程及边界见[派发验收](package-history-dispatch-acceptance.md)。未装配默认不可用，元数据可见不授训练或评估资格。

固定整包编写已在 [输入捕获与核对](authoring-package-input-acceptance.md) 和 [B2 手动生成与候选发布](package-authoring-frontend-acceptance.md) 后接通输入采集界面、明确采纳正文、精确构建及明确入包，操作见下节。上述 SQL 均未进入默认 BASE 或 v14 恢复清单，不能只启用默认预览就宣称整套研究／固定编写功能已经装配。当前范围和环境限制见 [检查点 15 验收](authoring-capture-adoption-build-acceptance.md)。

## 9. 固定整包章节候选与章节历史

### 明确选择已保存输入，手动生成

在项目「可复用任务」点击「新建固定整包编写模板」，读取固定输入目录并明确选择一份，核对双包修订、清单、事实与正文目标，再填写名称和编写要求。目录不会默认选择首条或最新条。没有保存输入时，可点击「采集新的固定编写输入」。

采集表单依次选择投标包与招标补遗包的确切修订、需求清单、已保存正文快照、章节和稳定文字节点。随后明确选择事实集及五个业务编号，再勾选实际需要使用的事实，逐条说明作用对象与用途。完整核对后点击「保存这份固定编写输入」。未保存选择会保留，刷新目录不会替换已选修订；保存回执丢失时用「恢复原保存请求」重放原请求与原键。新输入保存成功后可直接用于当前模板或私有草案。

保存后，再明确点击「手动生成固定整包章节候选」。已配置的服务可能调用模型并产生费用；本轮软件验收未调用付费模型。生成后打开指定任务，分别查看运行与候选发布状态，核对完整原稿、拟稿与具体增删，再进入原候选操作卡决定是否采纳。

同样可以打开「用自然语言拟定任务草案／恢复已有草案」，将来源切换为固定整包输入并明确选择。生成的是本人私有可编辑草案；「只保存可编辑草案」与「保存为固定整包编写模板，不运行」分别保留原意图。出现丢失回执时使用对应恢复入口，使用原请求和原键。

相同编写内容已有原任务时，按返回的固定链接查看原任务；改模板名、复制模板或重存相同输入不会授权额外调用。费用未核清时保持待核状态，不通过新模板绕过。服务未安装或未配置时仍可阅读已有模板与历史，不能把保存成功解释为执行能力已就绪。

### 明确采纳、生成文件与入包

操作卡会重新读取并核对完整固定输入、目标原文及当前采纳能力。核对后明确确认采纳，服务在同一事务内保存新章节修订、固定来源资格和新快照。重复确认不会追加第二次正文；回执丢失后仍从原卡恢复原请求。界面继续核对实际新快照与章节资格，不能把一次 HTTP 成功直接当成正文已经改变。

打开采纳结果对应的稿件，可以浏览章节和历史。当前首版仅支持纯文字稳定节点；含固定整包修订的稿件暂不开放普通手改、结构变更、旧版恢复、富文本导入或批次修改，避免丢失来源绑定。后续修改可重新明确采集这份已保存快照，再生成并采纳下一轮单节点候选。已存在的待确认保存请求仍可按原请求恢复。

生成时明确选择 Word／PDF，核对实际构建记录。没有冻结排版结构的采纳稿使用现有内置正文模板；已经冻结结构的稿件继续使用其对应模板。生成后，成功且经完整字节核验的文件才能通过明确的采用动作追加到投标包的新修订。构建、入包前都会重查来源和事实，原包及历史修订继续保留。

本轮真实 Word 生成与入包已验证；当前验收环境没有受控 Docker 转换证明，PDF 返回不可用。Word 成功不能代替 PDF 成功，也不授予正式投递资格。来源后来失效时，原正文、生成详情和旧操作回执仍可查阅，新用途按当前依据重新核验。

### 可选装配

在已有基础 schema、独立 API／Worker 运行角色及相应来源／要求权限之上，可选扩展依次为 `authoring-package-inputs.sql`、助手 `assistant.sql`／`live-facts.sql`／`intent-budget.sql`、`authoring-package-jobs.sql`、`authoring-exact-revisions.sql`、`authoring-exact-builds.sql`。这些文件沿用各自原有依赖和安装说明；不能让业务进程借用 owner 权限补齐缺失权限。

采用能力同时检查 API 所需存储和执行权限，缺少安装或权限时明确不可用。Worker 保留受约束的快照／构建 RPC，没有获得事实表或修订资格表的直接读取权限。默认预览与 v14 恢复仍不自动安装这些扩展，收费模型通道须按既有配置另行启用。

### 完整核对后恢复章节历史

在章节历史中明确选择原修订，先打开完整正文，核对段落、表格和图片；也可查看与当前已保存正文的具体文字变化。读取与比较均不会修改正文。

确认恢复时先处理当前未保存编辑；原历史图片和正文核验通过后，使用当前修订条件追加一个新版本，原版本保留。来源撤回、图片失效、项目关闭或修订竞争仍会阻止恢复；保留预览和输入，根据实际返回结果继续处理。

原章节历史功能的完整验证见 [检查点 14 回执](authoring-b2-history-regression-receipt.json) 与 [历史验收](authoring-history-acceptance.md)；本轮固定输入、采纳及构建的增量验证见 [检查点 15 验收](authoring-capture-adoption-build-acceptance.md)。

## 10. 严格整包历史研究：明确准入、冻结方案、核对独立结果

研究使用已冻结的确切范围、实交和已核对官方标签；CPU mean／median常数基线用于验证回溯机制，正式图文三评和模型发布仍另行实现。任务派发有独立可选入口，不随本界面或默认预览启动。缺少真实配对资料时不形成真实预测精度结论。

### 从项目内保存一份明确准入

1. 在项目“整包核查”的技术范围中，明确打开一份已保存范围；将“技术范围检查用途”选为“历史样本条件”。
2. 点击“读取实交记录”，选择这份包修订的实际提交，再“读取该实交的成绩记录”并明确选择官方成绩。不需要手工输入业务 UUID，也不会默认选最新记录。
3. 在“保存整包历史研究准入”中点击“读取所选记录的严格准入依据”。核对原实交／历史截止、原范围冻结、官方标签知晓时间、技术分与满分；官方零分正常显示，未知值保持未知。
4. 明确选择一份“独立核验回执”，填写原因，核对来源类别与缺项后勾选确认，再点击“明确保存这份历史研究准入”。缺少匹配证明、完整范围或当前来源条件时不能保存；合成机制资料的例外只供显式机制验证，不使外部证据条件自动成立。
5. 回执不明时使用“恢复原准入请求结果”。恢复保留原实交、原成绩、原正文、原条件头与原请求键；切换检查用途不会替换它。结果提示的是原请求保存回执，后续研究还会重新核验当前依据。

切换检查用途保留已填写原因和未决原请求。离开技术范围或整个工作面时，未发送输入受离开保护；已保存恢复记录按成员与范围隔离。需要新的准入对象时，重新明确选择并读取其依据。

### 在评分研究中明确选择输入并冻结方案

进入全局“评分研究”，默认是“整包历史研究”；只有明确打开“既有单稿研究记录”才进入旧记录工作面，旧记录不会自动转成严格整包输入。

1. 在“1. 选择已准入资料”点击“读取准入资料目录”。逐条“核对资料 … 的准入详情”，在本次读取仍有效时点击“明确选入研究方案”。目录只是发现记录，读取目录不授新的执行资格。
2. 为每份已选资料明确指定拟合、开发选择、区间校准或最终评估用途。界面要求至少两个拟合、一个开发选择和一个最终评估输入；真正的独立关联组与可用标签仍由服务端核对，不能用界面计数代替。
3. 在“2. 冻结研究方案”选择一份已冻结 CPU 协议；也可展开“冻结新 CPU 研究协议”，读取当前 CPU 方法，核对随机种子和组级重采样次数，填写原因并明确冻结。保存协议不会启动训练或访问付费模型。
4. 核对实交分界与标签可用截止。普通输入明确使用北京时间 UTC+08:00；需要复用精确边界时，勾选“使用含时区的精确时间（可保留微秒）”，填写完整 ISO 8601 时间及 `Z` 或 `±HH:MM` 时区，最多保留六位小数。精确输入按原值保存，不舍入；原实交与训练冻结时间仍由原记录及服务端固定。
5. 填写原因，核对协议、全部输入用途和两条边界，明确冻结研究组。服务端按完整关联组处理跨分界排除与迟到标签，实际成员结果应重新核对；最终集曝光后不能通过重新选择样本调整结果。

三个步骤间保留未发送输入。重新读取目录不会替换已发送的原请求；目录未配置表示数量未知，已观察到的空目录才表示该次观察为空。目录变化或分页不一致时停止合并，重新读取后再选择。

### 登记任务与等待独立执行

在“3. 任务与结果”可读取研究组目录并明确打开一组，也可接着查看刚冻结的研究组。先核对当前依据、实际成员、用途、排除与时间；当前依据变化时，不再允许新任务或恢复执行。

选择“训练 CPU 常数基线”或“独立最终评估”，填写原因并确认后，点击“明确创建研究任务”。独立最终评估需要同一研究组的已冻结训练结果，最终集曝光按服务端协议持久记录。同组同类任务复用原任务，不形成第二份研究结果。

**“任务已登记／等待独立执行”不表示训练或评估完成。** 默认运行配置不启动研究消费者。单份明确执行使用[`package_history_worker.py`](../../deploy/package_history_worker.py)；有界派发使用[`package_history_dispatcher.py`](../../deploy/package_history_dispatcher.py)，须先安装额外SQL并分别提供train／evaluate私有profile。核验、训练、评估保持独立非owner权限，API不借用这些凭据；启动方法及实际边界见[派发验收](package-history-dispatch-acceptance.md)。

### 查看、控制与恢复

- “读取组内任务目录”后明确打开任务，或在当前任务点击“读取所选任务当前状态”。当前状态单独读取，与原受理 ACK 分开展示。
- 暂停、恢复或取消均需选择动作、填写原因并核对当前代次。412 表示原条件已变化：保留原因，重新读取当前状态并重新确认，不能换新键自动重发原动作。
- 网络中断、回执无法核对或恢复前权限不足时，使用上方“恢复原研究请求结果”；它沿用原正文、原条件头与原幂等键。在原请求核清前不发起另一写入。
- 训练完成后可读取固定模型与基线结果；评估完成后分别查看全体记录与已核官方来源子集。总分母、成功／失败／拒绝／未标注、原量尺误差、配对基线、未知区间均保留，不将未知值补零。
- 来源后来失效不改写原准入、研究组或结果。已有历史是否可读仍取决于读取权限和依赖完整性；历史可读不授新用途资格，也不证明未来预测或正式投递资格。

### 装配与验收边界

严格历史 SQL、共同暴露守卫与研究目的角色仍是可选装配，不随 BASE、默认 Fusion v14 或其恢复清单自动启用。按已有安装与角色文档核对；缺少装配时显示明确不可用，不能用 owner 修补业务权限或用界面可见代替能力就绪。

本批真实 PG17 和公开 main 路由验证使用显式合成业务资料、证明与标签，CPU 实际执行且付费／供应商调用为 0；原件端口为显式合成内存实现，不宣称本批真实 S3 或 Kafka 运输。浏览器使用真实组件与原生 HTTP 原文重放，单独记录。具体命令、源码指纹、失败修正及最终集成结果见 [检查点 16 统一验收](package-history-ui-acceptance.md) 和 [集成回执](package-history-ui-regression-receipt.json)。
