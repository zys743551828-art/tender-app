# AI 投标工作台产品化方案

本文是当前方案的整合入口，说明产品、评分、检索和技术建设如何组成一条工作链。详细业务行为统一维护在[AI 投标工作台 PRD](AI投标工作台PRD.md)，算法与验收统一维护在[评分预测训练与验收方案](../05-技术与设计/评分预测训练与验收方案.md)，架构与运行契约统一维护在[全新系统技术方案](../05-技术与设计/AI投标工作台全新系统技术方案.md)。本文不另设字段、状态或精度门槛。

## 1. 产品定位

公司内部市政工程投标工作台，围绕否决风险与技术评分工作。用户上传资料、看懂问题、修改技术标、登记实际提交和正式结果，系统积累可追溯案例，并用独立评测决定是否升级评分模型。新系统从零设计，旧系统用于了解业务与保留历史事实。

用户看到三个入口：当前投标、历史项目、企业知识。项目中以对话发起任务，卡片承载结果和明确操作，原文按需查看；上传、复评、搜索和登记都有直接按钮。用户不需要理解检索、模型或训练流程。

项目保存资料、稿件、任务与正式结果；会话保存讨论；历史项目是这些项目的档案视图；知识是有来源、适用条件和发布状态的可复用内容。关闭会话、项目归档与知识停用分别处理，生命周期以PRD第4—5节为准。

## 2. 从一次投标到持续改进

~~~mermaid
flowchart LR
  A[上传招标补遗和技术标] --> B[解析与原页证据]
  B --> C[否决强制核对与逐项判断]
  C --> D[问题卡与有资格的评分预测]
  D --> E[改稿复评并登记实交版本]
  E --> F[正式成绩核验配对]
  F --> G[受控训练与独立评测]
  G -->|验收后发布| D
  H[历史项目与已发布知识] -->|按用途选择参考| C
~~~

系统先回答“哪些要求存在风险、哪些评分要点没有做好、证据在哪里”。评分模型通过验收且适用时，再回答“预计技术分是多少、可信区间多宽”。未经验证的判断与估计保留明确身份，不能显示成正式成绩或已经可靠的预测。

改稿建议来自逐项判断与工程依据；复评使用新稿并保留旧稿。分差只有在相同评分办法和冻结方法下才可比较，不能承诺某条修改一定带来官方加分。没有分项官方成绩时，系统发现的失分点也不等于评委实际扣分原因。

正式成绩绑定实际参加评审的提交稿，而非最新草稿。历史回测与真实投标前预测分别保存。成绩回流先核验和准入，再进入候选模型实验；不因新增案例或训练误差降低就自动替换线上模型。

## 3. 评分采用四层路线

| 层次 | 负责的工作 | 关键边界 |
| --- | --- | --- |
| 评分结构与章节准备 | 提取评分项、满分、档位、要点及例外；建立正文章节树和原页证据 | 同一生效资料和方法可缓存；补遗、方法或正文版本变化须更新相应产物 |
| 大模型逐项判断 | 读取完整相关章节及必要图表；判断档位、覆盖、针对性、具体性，每项重复3次并带出处 | 超长内容分层处理并记录覆盖；分歧是候选特征，三次一致不证明正确 |
| 统计模型学习分数 | 将逐项判断、结构和事前背景映射为正式技术分，比较正则线性、保序与近邻等方法 | 第一条基线不使用带成绩近邻和锚点；所有监督特征严格限于训练来源 |
| 比较式锚定对照 | 与同评分办法、已知分数的可比历史标书逐项比较 | 按独立评测的收益、偏差和费用决定是否启用，不是首版必需能力 |

大模型负责有证据的内容判断，统计模型负责与官方量尺对齐。约300份案例用于训练和验证低维监督模型，起步不训练长篇深度模型。区间来自经过独立检验的误差与校准过程，不能用三次大模型输出的波动替代。

首要验收是：在未见项目上，绝对误差稳定优于历史均值等基线，同时控制大误差、系统偏高偏低、复跑波动、失败覆盖和区间宽度。有同场配对正文才验证稿件间排序；技术入围概率还需入围规则、实际正负结果和事前可用特征，单独校准。技术分、技术入围与中标是不同目标。

具体数据准入、划分、防泄漏、建议门槛与发布条件见评分主规格，本文不把建议数值当作已经达到或已经认可的指标。

## 4. RAG与模型适配层如何支撑评分

| 能力 | 作用 | 对正式评分的约束 |
| --- | --- | --- |
| 文档与证据 | 解析文字、表格和图页，统一页码、坐标、版本与读取缺口 | 关键内容漏读不能靠校准系数补救 |
| 当前项目检索 | 定位规则对应章节、交叉引用与证据 | 检索定位后组装完整相关章节；固定少量片段不能代替整章 |
| 历史与知识检索 | 为建议提供有来源且适用的参考 | 其他项目的条件和企业事实不能自动成为当前项目事实 |
| 受控近邻与锚点 | 给统计模型或比较实验提供训练来源参考 | 与普通知识检索分开，按实验折、同源组和时间隔离正文、成绩及派生产物 |
| 大模型API适配 | 统一生成、结构化判断、视觉、Embedding与重排的能力配置、调用记录及预算 | 正式评分固定模型与方法；故障不得静默换模型、缩上下文或把错误当0分 |

RAG提升查找与依据质量，不能单独保证评分接近官方成绩。模型适配统一业务端口，不假定各家OpenAI兼容接口在结构化输出、视觉、工具、上下文和流式计费方面完全一致；供应商由真实资料质量与费用对照选出。

正式评分由专门的输入构建器从冻结版本取资料，不继承完整聊天历史。目标成绩、评委意见、事后改稿，以及携带这些信息的知识、摘要和缓存均受隔离。最终测试不用于反复调整提示词或挑选模型。

## 5. 工程形态与职责

推荐React＋TypeScript前端、FastAPI／Python领域服务、PostgreSQL＋pgvector、独立后台执行和私有对象存储。统一模型端口和独立评分实验服务连接业务链路。执行底座尚未冻结：首版固定任务优先比较成熟队列与普通Python或有界LangGraph，跨步骤持久执行再比较Temporal，官方Agent Server另核对部署与授权。公开证据与采用条件见[执行路线复核](../01-背景与市场研究/AI执行与工作流选型复核.md)及[相似产品核查](../01-背景与市场研究/相似AI产品技术路线核查.md)。

业务数据库保存项目、版本、正式决定和发布资格；对象存储保存不可变原件与产物；工作流管理长任务、重试与等待；模型提出判断和操作建议。正式写入仍经过领域校验、幂等事务和审计，聊天文字不能直接改变业务事实。

起步以模块化领域服务配合独立Worker部署，不把全量知识平台、多Agent或更多中间件作为评分验证前提。模型调用发生在数据库短事务之外，重试可能产生额外计费，需要明确预算与调用记录。

## 6. 建设重点与首个交付

当前重点是先验证评分链路。以下是交付优先级摘要，正式阶段与退出条件见PRD第19节及技术方案第16节。

| 优先级 | 可核对的交付 | 决策依据 |
| --- | --- | --- |
| 第一：评分最小链路 | 入库核验、规则提取、完整章节包、三次判断、证据回看、调用成本与失败清单 | 用首批10—20份真实案例检查资料和判断质量，发现是规则、解析还是模型问题；不据此宣布精度达标 |
| 第二：统计模型对照 | 按项目／模板／近重复正文分组，比较无带成绩近邻和锚点的基线，再分别做近邻及锚点消融 | 方法在开发数据中选择，最终独立项目用于一次验收；不达标就限制能力或补数据 |
| 第三：项目工作闭环 | 对话卡片、改稿复评、实际提交、成绩回流和观察发布 | 最小工作台与评分实验并行；正式使用仍须满足否决／强制核对、提交和运行门槛 |
| 第四：知识复用与稳定运行 | 少量高价值知识、失效影响、全量档案、容量与恢复演练 | 用真实复用价值决定扩大范围；基本私有存储、来源隔离与备份从首次入库起提供 |

评分实验不等待完整工作台、全量历史检索或企业知识页面。基础身份、版本、证据、隔离与模型端口建立后，可通过受控实验入口先完成评分验证；该入口不具备正式业务发布或实际提交的权限。

第一项交付应能展示一份稿件的评分规则、逐项判断及出处、读取覆盖、三次分歧、运行费用和失败原因。正式成绩由标签核验与评测通道单独读取，用于分析误差。结果能明确指向下一步修正哪一环，避免只得到一个无法解释的总分。

## 7. 状态与阅读入口

产品与技术规格、候选调研、五组隔离机制实验已经形成；完整新系统、真实解析质量、真实模型API兼容性、正式评分误差与区间覆盖仍需实现和真实材料验证。机制实验不代表预测精度已通过。

首批案例建议提供实际提交技术标、最终招标文件及全部补遗、正式技术分及满分、成绩出处、项目身份与时间。有分项、评委明细和同场资料时一并保留；缺失项列明，不补造。资料模板和数量建议以评分主规格第2节为准。
